# YOLO 页面 CPU 显示与推理减负

## 工作事项

- 页面右上角每秒显示一次整机 CPU 占用，底部保留 YOLO 实际推理帧率、目标数和单次耗时。
- 相机的 RGB888 转换改为推理线程请求新帧时才执行；预览序号未变时不重复触发画布刷新。
- 320×240 输入到 640×640 模型的常用两倍放大路径改为逐像素复制与整行复制。
- 应用限时退出时主动停止推理线程和相机，避免可连接线程析构触发 `terminate`。

## 架构与实现原理

采集线程仍按摄像头速度更新 320×160 的 RGB565 预览。YOLO 推理线程调用 `cam_frame_rgb()`，若没有新 RGB 帧则设置请求位；采集线程下一帧才执行 NV12→RGB888，并递增 RGB 帧序号。推理线程读到后清除“未读”状态，做 letterbox、RKNN 推理、解码与 NMS。这样采集帧率和推理帧率可以不同，避免对从未送入模型的帧做 RGB 转换。

UI 定时器仅在 YOLO 页面活跃时工作。CPU 数值取 `/proc/stat` 相邻采样的非空闲时间比例，是**整机占用**，不是单独的 YOLO 线程占用；采样间隔为 1 秒。推理帧率由推理线程完成的次数统计，不是摄像头采集帧率。

## 板上验证

RV1106、320×240 NV12 采集、640×640 YOLOv5s RKNN 模型，限时运行 15 秒；日志中稳定阶段为 **9.0–10.0 次推理/秒、87–93 ms/次、整机 CPU 31%–41%**。模型正常检出目标。第二次测试验证退出码为 0，推理线程与相机均正常清理。

第三次测试用 `YOLO_STATS_LOG=1` 拆分一次推理耗时：**letterbox 约 1.6 ms，`rknn_run` 约 84–86 ms，后处理约 2–7 ms**。因此当前速度主要受模型在 NPU 上的运行时间限制；继续优化 CPU 预处理，对总帧率的影响有限。要显著高于约 10 次/秒，应评估更小的 RKNN 模型或更小的模型输入尺寸，并同时验证精度变化。

## 置信度偏低的原因与注意事项

当前送模型的原始图只有 320×240，再放大到 640×640 并不会增加细节。画面中目标小、逆光、模糊或训练集分布不匹配，都可能使分数停留在 30%–40%。代码中的分数是**目标存在概率 × 类别概率**；仅提高显示值或降低阈值不能提高真实置信度。要验证改善，应在同一目标、相同光照和距离下，比较更高分辨率采集或针对实际场景优化模型后的分数、召回率、推理速度和内存。

板子只有 54MB 内存，当前相机与 NPU 同时运行时可用内存较紧。直接将全局采集尺寸改为 640×480 会增大 V4L2 缓冲、预览转换和 RGB 缓冲，也会影响相机页；需做独立模式与压力测试后再采用。当前改动保持模型与分数公式不变。

## 后续工作

- 对相同场景记录多帧的类别、分数、推理耗时，建立可信的对照数据。
- 对较小输入尺寸、轻量模型做同场景 A/B 测试，比较帧率与检测分数。
- 若需要更高置信度，优先验证高分辨率输入与针对目标场景重新训练/量化的模型。
