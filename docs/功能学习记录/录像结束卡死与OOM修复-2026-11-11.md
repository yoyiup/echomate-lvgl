# 录像结束卡死与OOM修复（2026-11-11）

## 现象

录完视频后屏幕停在最后一帧，触摸无响应。SSH仍可连接，但 `lvgl_app` 已不存在，守护进程也无法重新拉起界面。

这不是普通UI卡顿。内核日志明确记录：

```text
Out of memory: Killed process 2193 (lvgl_app)
```

## 根因

### 1. `/tmp` 是内存盘

录像目录 `/tmp/cam` 位于27MB的tmpfs，文件会直接占用RAM。故障发生时：

- 640×480未压缩AVI：19.3MB。
- 多个H.265/MP4：约1.3MB。
- H.265封装残留raw码流：约0.3MB。
- `/tmp` 总占用23.5MB，系统可用内存最低约1MB。

随后H.265停止录像时启动 `ffmpeg`，raw码流和MP4短暂同时存在，ffmpeg本身也需要内存。RV1106只有54MB RAM且没有swap，最终内核选择杀掉 `lvgl_app`。

### 2. 旧空间保护只看文件系统

旧代码只要求 `/tmp` 留4MB，没有读取 `/proc/meminfo`。tmpfs剩余空间不等于系统仍有足够工作内存，4MB无法覆盖rkaiq、MPP、ffmpeg和网络服务的并发峰值。

### 3. 子进程继承单实例锁

主程序使用 `/var/run/lvgl_app.lock` 的 `flock` 防止多实例，但锁文件打开时没有 `O_CLOEXEC`。热点和手机传输进程经fork/exec后继承该fd。

主程序被OOM杀掉后，热点子进程仍替它持有锁。守护进程启动的新实例因此反复输出：

```text
[启动] 已有 lvgl_app 在运行，本次退出
```

屏幕便一直停在最后一帧。

## 修复架构

```text
开始/继续录像
    │
    ├─ 检查 tmpfs 可用空间
    ├─ 检查 MemAvailable
    ├─ 始终保留 12MB 系统安全余量
    └─ 不满足条件：拒绝启动或正常停止录像，LVGL继续运行

主程序单实例锁
    └─ O_CLOEXEC ─► exec热点/传输服务时自动关闭锁fd
                       └─ 主程序异常退出后锁立即释放，守护可重启
```

## 实现原理

### 资源保护

`cam_capture.cpp` 新增统一的 `record_resources_ok()`：

- `statvfs()` 检查录像目录可用空间。
- 读取 `/proc/meminfo` 的 `MemAvailable`。
- 两项都必须大于“12MB安全余量 + 下一步预计分配”。

AVI每写一帧前重新检查，资源不足时正常关闭AVI并回填索引。H.265启动前按6MB临时输出预算检查，为raw码流、MP4副本和ffmpeg留下空间。

### 锁生命周期

单实例锁改为：

```c
open("/var/run/lvgl_app.lock", O_RDWR | O_CREAT | O_CLOEXEC, 0644)
```

`O_CLOEXEC` 不影响主程序持锁，但外部服务exec成功时会由内核自动关闭该fd，避免锁泄漏到长生命周期子进程。

## 板端验证

1. 故障录像已先备份到电脑，所有MP4/AVI均可被ffprobe读取。
2. 清理19.3MB AVI后，`/tmp` 使用率从87%降到14%，可用内存从约7MB恢复到约27MB。
3. 修复版AVI自动测试生成14.9MB、17帧文件后，应用仍存活，内核无OOM记录。
4. 保留该AVI再尝试H.265，程序正确提示“可用内存或临时空间不足”，拒绝启动编码，应用继续运行。
5. 杀掉测试实例后，新实例能立即取得锁，守护进程正常运行。
6. 最终正常状态：`/tmp`约0%使用，可用内存约33MB，`lvgl_app`由守护进程运行。

## 注意事项

1. AVI是640×480未压缩BGR，约7.37MB/s；即使有保护，也只适合短时调试。
2. H.265仍是推荐录像格式，但开始前若有大AVI占用tmpfs，会被安全地拒绝；应先通过相册/手机传输备份并清理旧视频。
3. 不要把tmpfs的“剩余容量”当成独立存储空间，它和应用共享同一批物理RAM。
4. H.265封装成功后会删除 `.h265` 临时码流；若进程被强杀，可能遗留该文件，需要下次启动或人工清理。
5. 板上的 `/mnt/sdcard` 当前不是实际挂载的SD卡，而是rootfs目录，不能作为大容量录像盘使用。
