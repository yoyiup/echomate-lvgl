# H.265偶发花屏修复（2026-11-11）

## 现象

部分H.265录像会突然出现大面积灰色块、残影和画面撕裂，并持续若干帧后恢复。该现象不是普通低码率马赛克。

对故障录像执行严格解码，FFmpeg报告：

```text
Could not find ref with POC 22
Could not find ref with POC 10
```

备份的3段录像中有2段出现参考帧错误。对残留的原始 `.h265` 码流解码也出现相同错误，因此损坏发生在MPP输出写文件阶段，不是MP4封装造成。

## 架构与故障位置

```text
V4L2 NV12 DMA-BUF
    │
    ├─ dup fd并导入MPP
    │
    ├─ encode_put_frame（异步）
    │       └─ 旧实现立即buffer_put  ← 输入生命周期风险
    │
    └─ encode_get_packet
            └─ MPP环形输出DMA-BUF
                    ├─ 尾部数据
                    └─ 头部数据
                         旧实现跨尾时offset=0  ← 码流字节损坏
```

H.265的P帧依赖前面的参考帧。一个参考访问单元损坏后，后续P帧仍会引用它，于是错误会扩散成大面积灰块和残影，直到下一个IDR关键帧才可能恢复。

## 根因一：环形输出跨尾处理错误

MPP输出DMA-BUF是环形缓冲。访问单元可能从缓冲尾部继续到缓冲头部。旧代码在：

```text
offset + len > buf_size
```

时直接执行 `offset = 0`，然后从缓冲头连续写 `len` 字节。这会丢掉真正位于尾部的数据，并混入不属于当前访问单元的字节。

修复后按两段写出：

1. `offset` 到 `buf_size` 的尾部。
2. 剩余长度从缓冲头开始。

同时严格检查 `offset < buf_size`、`len <= buf_size`；范围异常时不再猜测偏移。

## 根因二：输入DMA-BUF释放过早

SDK头文件明确说明 `encode_put_frame()` 是异步接口。旧实现调用成功后立刻 `buffer_put()`，随后才调用 `encode_get_packet()`。

即使V4L2原始fd仍然存活，MPP导入对象和硬件映射的生命周期也可能已经结束。系统负载和硬件时序不同，就会出现“短录像正常、某些录像偶发损坏”。

修复后顺序为：

```text
导入MppBuffer
  → encode_put_frame
  → encode_get_packet
  → 完整写出码流
  → release_packet
  → buffer_put输入MppBuffer
  → 返回采集层并QBUF给ISP
```

这仍然是真正的DMA-BUF零拷贝，只延长缓冲所有权，没有增加像素复制。

## 注意事项

1. “文件能打开”不能证明码流正确，必须全量解码并检查错误输出。
2. 只测试几十帧不足以证明环形缓冲正确；输出累计长度必须多次越过缓冲边界。
3. 不要再次把 `buffer_put()` 移到 `encode_get_packet()` 之前。
4. 不要用 `offset=0` 掩盖越界；环形跨尾必须分两段处理。
5. `dup(fd)`仍然必须保留，避免MPP释放导入对象时关闭V4L2持有的原fd。
6. 当前GOP为30，即每秒一个IDR；这只能缩短错误传播时间，不能替代码修复代替。
