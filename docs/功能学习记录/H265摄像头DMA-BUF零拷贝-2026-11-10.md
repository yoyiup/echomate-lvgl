# H.265 摄像头 DMA-BUF 零拷贝

## 目标

让 RV1106 摄像头采集到的 NV12 帧直接进入硬件 H.265 编码器，不再经过应用层整帧 `memcpy`，同时保证 ISP 与 VENC 不会并发读写同一个缓冲区。

## 原来的数据路径

```text
ISP -> V4L2 MMAP buffer -> memcpy -> Rockit MMZ buffer -> VENC
```

即使 MMZ 池只在启动时申请，320×240 NV12 的 115200 字节仍需每帧复制一次。CPU 还要承担 LVGL 预览色彩转换，所以录像时负载会明显增加。

## 新的数据路径

```text
ISP -> V4L2 MMAP/DMA-BUF -> Rockit 外部 MB -> VENC
                 同一块物理内存
```

1. `VIDIOC_REQBUFS` 申请 4 个 V4L2 MMAP 缓冲区。
2. 对每个缓冲区调用 `VIDIOC_EXPBUF`，得到对应的 DMA-BUF fd。
3. H.265 开始录像后，使用 `RK_MPI_SYS_CreateMB` 将 fd、映射地址和大小包装成 Rockit `MB_BLK`。
4. `RK_MPI_VENC_SendFrame` 直接接收这个 `MB_BLK`，不再分配输入 MMZ，也不复制 NV12。
5. 用 `RK_MPI_MB_InquireUserCnt` 检查 VENC 是否已释放该帧；只有引用计数回到基础引用 1 时才重新 `VIDIOC_QBUF`。

## 为什么不能提交后立即 QBUF

`SendFrame` 是异步接口。调用成功仅表示 VENC 接收了任务，不表示硬件已经读完像素。如果立即 QBUF，ISP 可能开始覆盖该 DMA-BUF，而 VENC 仍在读取旧帧，结果就是块状马赛克、花屏或偶发坏帧。

因此，真正零拷贝的核心不只是“共享 fd”，还包括缓冲区所有权流转：

```text
V4L2 DQBUF -> 应用/预览读取 -> VENC 持有 -> VENC 释放 -> V4L2 QBUF
```

## 架构变化

- `CamCapture`
  - 保存每个 V4L2 buffer 的导出 fd。
  - 保存哪些 buffer 正被 VENC 持有。
  - 编码期间每 5ms 检查一次已完成 buffer，及时归还 ISP。
- `H265Recorder`
  - 删除预分配 MMZ 输入池。
  - 删除整帧 `memcpy` 和输入缓存 flush。
  - 缓存 DMA-BUF fd 到 `MB_BLK` 的包装关系。
  - 销毁 VENC 通道后释放包装句柄，但不关闭 V4L2 拥有的 fd 和 mmap。

## 注意事项

1. 当前采集格式必须是单 plane、连续布局的 NV12；Y 后面紧跟 UV。
2. DMA-BUF fd、mmap 和 Rockit 外部 MB 的生命周期必须严格有序：先销毁 VENC/MB，再关闭 fd 和解除 mmap。
3. 不能仅靠固定延时猜测编码完成，必须依据媒体缓冲引用计数。
4. 4 个采集 buffer 允许 ISP 与 VENC 流水并行；如果 VENC 长时间占满所有 buffer，采集会自然背压，而不会覆盖正在编码的帧。
5. 这里消除的是“摄像头到 H.265 编码器”的复制。LVGL 预览仍需读取 NV12 并转换为 RGB565，这部分不是编码输入复制。

## ★★★ 实测踩坑：`mpp_buffer_import_with_tag()` 会接管 fd 所有权

这是整条链路最隐蔽的一个坑，症状和「VENC 卡死」几乎一模一样，但根因完全在别处。

### 症状

首三帧编码完全正常（`get_packet rc=0`、`wrote=531/158/208`、`packet released rc=0`），
但第 4 帧之后：ISP 不再出帧、采集线程永久卡在 `poll()`、`.h265` 停止增长、
`cam_record_seconds()` 不前进、自动停止不触发、`stop()` / `remux_mp4()` 从未被调用。
**屏幕上表现就是「卡在最后一帧」**，极易误判成 VENC 阻塞或死锁。

### 决定性证据

| 检查项 | 结果 | 含义 |
|---|---|---|
| `/proc/<pid>/fd/{8,9,10,11}` | 全部「已关闭」 | V4L2 的 4 个 DMA-BUF fd 全丢 |
| 三帧 `output fd` | 恒为 `9`，与 frame=0 输入 fd 相同 | fd 9 被关后被 `VALLOC_IOCTL_MB_GET_FD` 复用 |
| `/proc/<pid>/task/*/wchan` | 采集线程在 `poll_schedule_timeout` | 没人阻塞在 VENC 上，是 V4L2 不出帧 |
| `录像结束：%d 帧` 日志 | 不存在 | `stop()` 从未调用 |
| 手动跑同一条 ffmpeg | `rc=0` | 封装命令没问题，是 `remux_mp4()` 没执行 |

### 根因

`mpp_buffer.h` 里那句 `Transfer a external buffer info to MppBuffer` 的 **Transfer 就是所有权转移**：
import 之后 `MppBufferInfo.fd` 归 MPP 所有，`mpp_buffer_put_with_caller()` 会把它 `close()`。

原代码每帧把 V4L2 的 DMA-BUF 原 fd 直接传进去再 put，等于**每帧关掉一个 V4L2 buffer 的 fd**。
4 个 buffer 的 fd 全被关后 ISP 停止出帧，采集线程在 `poll()` 上永远等不到数据 —— 后面所有异常都是这一条的连锁反应。

### 修法：`dup()` 隔离所有权，仍然零拷贝

```cpp
/* dup 只复制进程 fd 表的一个表项，新旧 fd 指向同一块 dma_buf
 * （同一物理内存），不复制帧数据 —— 零拷贝性质不变。 */
const int import_fd = ::dup(fd);
...
info.fd = import_fd;

MPP_RET rc = api_->buffer_import(nullptr, &info, &buffer, kTag, "submit_dmabuf");
if (rc != MPP_OK || !buffer) {
    ::close(import_fd);   /* MPP 未接管，副本自己收 */
    return -1;
}
```

修完的实测证据（`frame=60`）：

```text
[APP ] MPP zero-copy: frame=60 import src_fd=9 dup_fd=43 rc=0
[APP ] MPP zero-copy: frame=60 packet released rc=0
[APP ] MPP zero-copy: frame=60 done src_fd=9 alive=1
```

`src_fd=9` 与 `dup_fd=43` 是**两个不同 fd 指向同一块内存**；MPP 关掉 43 后 `src_fd=9` 仍 `alive=1`。

### 为什么 `mpp-test` 从不踩这个坑

它不走 import，而是 `mpp_buffer_get` 自己申请 buffer 整程复用，生命周期和 fd 所有权完全在应用手里。
**凡是从外部（V4L2 / DRM / ION）import 进来的 fd，交给 MPP 前先 dup 一份。**

## 板端实测结果（2026-11-10）

| 指标 | 实测值 |
|---|---|
| 录制时长 | 2.10 秒（`录像结束：63 帧 / 2 秒`） |
| 帧数 | 63 帧 |
| 有效帧率 | 30 fps |
| 封装 | MP4 / `codec_name=hevc` / 320×240 |
| 文件大小 | 71116 字节 |
| `alive` 校验 | frame 0→62 **全程 `alive=1`** |
| GOP 结构 | 每 30 帧一个 I 帧，其余全 P（无 B 帧） |
| raw `.h265` | remux 成功后已 `unlink` |

**画面校验**（逐帧亮度均值）：前 5 帧全黑（均值 0.0），第 6 帧起画面渐入，
尾部稳定在均值 96.6 / min 50 / max 137 —— 画面内容正常，不是黑屏。

> ⚠️ 前 5 帧全黑**不是 bug**：录制刚启动时 rkaiq 3A（AE）还在收敛，第一帧本身就是欠曝的。
> `ffmpeg` 解码时报的 `Could not find ref with POC 4 / POC 15` 同理 ——
> 这是「录制从半途开始、开头缺参考帧」的表现，只影响开头那几帧，
> 全程 63 帧、`nb_frames=63`、`nb_streams` 正常，不影响可播放性。
