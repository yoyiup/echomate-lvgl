# 拍照与录像升级到 640×480（2026-11-11）

## 目标

摄像头主采集分辨率由 320×240 提升到 640×480，使以下产物都保留完整 VGA 画面：

- BMP 拍照：640×480。
- AVI 未压缩录像：640×480、默认 8fps。
- H.265/MP4 硬件录像：640×480，帧率跟随摄像头实际输出。

LVGL 屏幕仍是 320×240，摄像头预览区仍为 320×160，不改变页面布局。

## 架构与数据路径

```text
SC3336 / ISP
    │ 640×480 NV12
    ├─► 居中裁剪 + 1/2 抽样 ─► 320×160 RGB565 ─► LVGL 预览
    ├─► NV12→BGR24 ─► 640×480 BMP
    ├─► NV12→BGR24 ─► 640×480 未压缩 AVI
    └─► DMA-BUF 零拷贝 ─► MPP H.265 ─► 640×480 MP4
```

采集仍使用 V4L2 单 plane NV12。640×480 一帧大小为：

```text
640 × 480 × 3 / 2 = 460800 字节
```

4 个采集缓冲合计约 1.8MB，比原 320×240 多约 1.38MB。

## 实现原理

### 1. 主采集尺寸

`cam_capture.hpp` 的 `kCapW/kCapH` 和 C 接口中的 `CAM_CAP_W/CAM_CAP_H` 统一改为 640×480。驱动若调整尺寸，代码仍以 `VIDIOC_S_FMT` 返回的实际尺寸为准。

### 2. 预览尺寸不变

`nv12_to_rgb565()` 已支持整数倍抽样：640×480 输入时横纵步长为 2，并从中央 320 行中抽样得到 320×160，保持比例且不拉伸。

### 3. 拍照

拍照原本就按 `cap_w_ × cap_h_` 分配 BGR 缓冲并写 BMP，因此提升主采集尺寸后自然输出 640×480，无需额外缩放。

### 4. AVI

原 AVI 固定使用预览尺寸 320×160。本次改为：

- `avi_open()` 使用实际 `cap_w_/cap_h_`。
- NV12→BGR24 转换输出实际采集尺寸。
- 空间检查按 640×480×3 计算。
- 921600 字节 BGR 转换缓冲在开始录像时申请一次，后续每帧复用，避免每帧申请大块内存。
- 修正 AVI 关闭时 `strh.dwLength` 的回填偏移：正确位置是 140。原代码写到 132，会把 `dwRate`（帧率）覆盖成总帧数，造成播放器速度异常。

### 5. H.265

H.265 本来就跟随采集尺寸，DMA-BUF 零拷贝路径不变。码率按像素数从原基准线性缩放：

```text
320×240：512kbps
640×480：2048kbps
```

这样分辨率提高4倍时，每像素可用码率不下降，避免因仍使用512kbps而产生明显马赛克。

> 后续新增了H.265专用1280×960选择档；BMP和AVI仍保持640×480。高清档码率因板端tmpfs与RAM限制封顶4.096Mbps，详见《H265录像分辨率选择-2026-11-11.md》。

## 注意事项

1. 板子只有54MB内存。640×480采集缓冲比原来多约1.38MB，必须观察 rkaiq、YOLO 同时运行时的可用内存。
2. AVI是未压缩BGR，640×480每帧约900KB；8fps约7.4MB/s。`/tmp` 只有约27MB，通常只能保存约2～3秒，空间保护会提前停止录像。
3. H.265仍是推荐录像格式，文件小得多，并且输入保持DMA-BUF零拷贝。
4. YOLO获取的RGB帧也变为640×480，细节增加，但NV12→RGB888转换量提高4倍；其按需转换机制保持不变。
5. 屏幕预览仍为320×160，因此提升分辨率不会增加LVGL canvas内存，但源帧读取和转换带宽会上升。
6. 不要移除H.265导入前的`dup(fd)`，否则MPP释放导入缓冲时会关闭V4L2原fd。
7. `CAM_AVI_AUTOTEST=1` 仅用于板端回归：摄像头就绪后自动录制约2秒并正常关闭文件；正常守护进程不设置该变量。
