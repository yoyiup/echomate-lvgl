# H.265 零拷贝性能对比（2026-11-11）

## 测试目的

确认摄像头 H.265 输入从“每帧申请 MMZ + 两次 `memcpy`”改为“V4L2 DMA-BUF 直接导入 MPP”后，对帧率、CPU、内存和文件体积的实际影响。

## 测试环境与口径

- 开发板：RV1106，单核 CPU，54MB 内存。
- 摄像头：SC3336，经 ISP 输出单 plane NV12，320×240，约 30fps。
- 旧 H.265：提交 `d159016`，Rockit VENC；每帧申请 MMZ，分别复制 Y、UV。
- 新 H.265：提交 `a104dd1`，MPP 导入 V4L2 DMA-BUF；无输入像素复制。
- 两版均运行同一个 `CAM_H265_AUTOTEST=1`，录制约 2 秒。
- CPU 使用 BusyBox `top`，录像期间每 0.3 秒采样，共 5 次。
- 内存读取 `/proc/<pid>/status`，使用 `VmRSS`，不把 `top` 的 VSZ 当物理内存。

> AVI 仅作用户体验侧参考：它是 320×160、8fps、未压缩 BGR，并非与 H.265 完全相同的编码参数。

## 实测结果

| 场景 | 进程 CPU | 整机忙碌 | 实际帧数 | VmRSS | 线程数 |
|---|---:|---:|---:|---:|---:|
| 仅摄像头预览 | 25.0% | 39.2% | 约 30fps 预览 | — | — |
| AVI 未压缩录像 | 28.8% | 45.8% | 14 帧 / 约 1.7 秒，8fps | 约 8MB | 14 |
| 旧 H.265（两次 memcpy） | 28.5%* | 约 47.8% | 61～62 帧 / 2 秒 | 9384KB | 17 |
| 新 H.265（DMA-BUF 零拷贝） | 28.3%* | 约 48.2% | 61～63 帧 / 2 秒 | 8040KB | 14 |

`*` 去掉 `top` 第一个包含相机/编码器初始化成本的样本，比较稳定录像阶段；旧版 28.5%，新版 28.25%。0.25 个百分点小于板端采样波动，应视为“平均 CPU 基本相同”。

### 内存变化

- `VmRSS`：9384KB → 8040KB，减少 **1344KB（约 14.3%）**。
- `VmSize`：51824KB → 44212KB，减少 7612KB。
- 线程：17 → 14。

新版不再加载 Rockit VENC 那套额外线程/映射，也不再按帧申请 MMZ 输入块，因此内存收益比平均 CPU 收益明显。

### 文件与吞吐

- AVI：14 帧约 2.15MB，约 153.6KB/帧。
- H.265：约 2 秒为 41～44KB（画面内容不同会波动）。
- 两版 H.265 均稳定达到约 30fps；新版本轮为 63 帧，DMA-BUF 原 fd 在第 30/60 帧均为 `alive=1`。

## 为什么去掉 memcpy 后 CPU 没明显下降

320×240 NV12 每帧只有 115200 字节，30fps 的输入复制带宽约：

```text
115200 × 30 = 3.456 MB/s
```

对 RV1106 来说，这段顺序内存复制不是主要 CPU 消耗。主要负载仍来自：

1. 每帧 NV12 → RGB565 的 LVGL 预览转换。
2. 屏幕刷新和 framebuffer/SPI 驱动。
3. ISP/rkaiq 线程及系统调用。
4. MPP 每帧的 DMA-BUF import/put，以及输出码流的 ioctl/mmap/fwrite。

因此零拷贝的主要价值不是让 UI 上的 CPU 数字立刻下降很多，而是：

- 删除每帧 MMZ 分配/释放和 3.456MB/s 的输入内存搬运。
- 降低内存占用及内存碎片风险。
- 让 ISP → VENC 数据路径成为同一块物理内存。
- 分辨率升高后，复制成本不会按像素数继续放大。

## 架构结论

当前零拷贝实现是正确方向，帧率没有回退，内存明显改善。若下一步目标是继续降低当前 320×240 下的 CPU，应优先优化预览链路，而不是继续折腾已经很小的编码输入复制：

1. 降低 LVGL 预览刷新率，但保持摄像头/录像 30fps。
2. 用 RGA 将 NV12 转 RGB565，替代 CPU 逐像素转换。
3. 只刷新画面变化区域，减少 framebuffer/SPI 提交。
4. 缓存 4 个已导入的 `MppBuffer`，避免每帧 `dup/import/put`；需要严格处理 fd 所有权和停止时释放。

## 注意事项

- 不要移除 `dup(fd)`：MPP 会接管传入 fd，直接传 V4L2 原 fd 会在 4 帧后把采集缓冲 fd 全部关掉。
- 后续长录像复测发现，旧实现过早释放导入的 `MppBuffer`，且未正确处理MPP输出环形缓冲跨尾，导致部分码流出现参考帧错误；现已修复，详见《H265偶发花屏修复-2026-11-11.md》。原文中的短时“无花屏”只能证明当次样本，不代表生命周期处理正确。
- CPU 对比必须去掉首个初始化样本，并至少采 4～5 次。
- AVI 与 H.265 的分辨率、帧率、格式不同，只能比较用户侧整体负载，不能当严格编码器基准。
- 文件大小受场景运动和亮度影响，不应作为编码正确性的唯一判断；应同时检查帧数和解码完整性。
