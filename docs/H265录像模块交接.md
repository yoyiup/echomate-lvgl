# H.265 录像模块交接文档

> 最后更新：2026-11-10 · 对应代码 `lvgl_app/src/cam/`
> 前置阅读：`docs/功能学习记录/H265摄像头DMA-BUF零拷贝-2026-11-10.md`（设计与踩坑全过程）

本文面向**接手这个模块的人**。目标：知道它在哪、怎么跑、为什么这么写、
出问题时第一步查什么。不需要重新读一遍设计推导过程。

---

## 1. 一句话说清

摄像头 NV12 帧**不经过 CPU 复制**，直接把 V4L2 的 DMA-BUF fd 交给
Rockchip MPP 硬件编码器出 H.265，停止时用 ffmpeg **无重编码**封装成 MP4。

**当前状态：已打通并板端验证**（63 帧 / 2.10 秒 / 30fps / 画面有效 / 资源正常回收）。

---

## 2. 数据路径

```text
ISP ──► V4L2 (MMAP + EXPBUF) ──► DMA-BUF fd ──► dup() ──► MPP import ──► VENC (硬编)
              │                    同一块物理内存，全程无 memcpy              │
              │                                                          H.265 码流
              └──► LVGL 预览（CPU 转 RGB565，这部分不是编码输入）◄── VALLOC_IOCTL_MB_GET_FD
                                                                          │
                                                                    mmap → fwrite(.h265)
                                                                          │
                                                          stop() → ffmpeg -c:v copy → .mp4
```

两条独立的零拷贝之外的关键点：

1. **输入零拷贝**：V4L2 buffer 的 DMA-BUF 直接当 VENC 输入，115200 字节/帧不过 CPU。
2. **输出零拷贝**：码流落在 `/dev/mpi/valloc` 的 DMA-BUF 里，`mmap` 后直接 `fwrite`，不是先拷到用户缓冲。

**调用链**：

```text
ui_camera.c 按钮 / AUTOTEST
  └─► cam_record_start_h265(path)          cam_capture.cpp:1078
        └─► CamCapture::record_start_h265  :934   → h265_.start() 建编码器、开 .h265
              └─► 采集线程每帧 handle_frame → h265_.submit_dmabuf()  (持 rec_mutex_)
                    └─► import → put_frame → get_packet → mmap → fwrite → release

ui_camera.c 停止 / 满 2 秒 / 达 10 秒上限
  └─► cam_record_stop() → record_stop()  :958
        ├─► h265_.stop()   → cleanup_encoder() + remux_mp4()
        └─► log("录像结束：%d 帧 / %d 秒")
```

注意：`submit_dmabuf()` 在**采集线程**里跑，且持 `rec_mutex_`；UI 侧 `record_stop()`
要拿同一把锁。如果编码器卡住，屏幕会停在最后一帧 —— 这是"板子卡死"的假象之一。

## 4. 五个关键设计决策

### 4.1 为什么交 fd 给 MPP 之前要 `dup()`

**这是本模块最大的坑，改代码时最容易踩回去。**

`mpp_buffer_import_with_tag()` 会**接管 `MppBufferInfo.fd` 的所有权**，
后续 `mpp_buffer_put_with_caller()` 会把它 `close()`（头文件里
"Transfer a external buffer info to MppBuffer" 的 Transfer 就是所有权转移）。

原代码直接把 V4L2 的 DMA-BUF fd 传进去再 put，等于**每帧关掉一个 V4L2 buffer 的 fd**。
4 个 buffer 全关后 ISP 停止出帧，采集线程永久卡在 `poll()`，
然后 `rec_sec_` 不再前进、自动停止不触发、`stop()`/`remux_mp4()` 都不执行 ——
**屏幕上就是"卡在最后一帧"**，极易误判成 VENC 阻塞。

```cpp
/* h265_recorder.cpp:232 */
const int import_fd = ::dup(fd);      /* 只复制 fd 表项，不复制帧数据 */
info.fd = import_fd;

MPP_RET rc = api_->buffer_import(nullptr, &info, &buffer, kTag, "submit_dmabuf");
if (rc != MPP_OK || !buffer) {
        ::close(import_fd);           /* MPP 未接管，副本自己收 */
        ...
}
```

`dup` 出来的 fd 指向**同一块 dma_buf（同一物理内存）**，零拷贝性质不变。

> **通用规则**：凡是从外部（V4L2 / DRM / ION）import 进 MPP 的 fd，先 `dup` 一份。
> `mpp-test` 不踩这坑是因为它走 `mpp_buffer_get` 自己申请 buffer，所有权一直在应用手里。

### 4.2 为什么每帧 import + put，而不是启动时 import 一次

当前实现是"每帧 import、put_frame 后立即 put"。这是**最小可用**版本：
4 个 V4L2 buffer 各自对应一次 import，成本在微秒级，实测 30fps 无压力。

缓存复用（启动时对所有 V4L2 fd 各 import 一次、`stop()` 统一 put）是可选优化，
能省掉每帧的 import/put 调用，但**必须先确保 dup 已生效**，否则一次 put 就把
V4L2 的 fd 关掉，症状和 §4.1 一样。没性能问题就别动。

### 4.3 为什么 `buffer_idle()` 恒返回 `true`

SDK 把 `encode_put_frame` 标注为 async，但 **RV1106 这版 MPP 实际是阻塞输入模式**：
`put_frame` 返回时 VENC 已读完像素。

依据：板端连续录制 63 帧无花屏/撕裂，且 `buffer_put` 之后 V4L2 原 fd 仍 `alive=1`
（日志心跳可查）。所以提交完即可归还 V4L2，不会出现"ISP 覆盖正在编码的帧"。

`held_by_venc` / `venc_held_[]` 那套标记仍然保留，是为了将来真要改成异步时
有个现成的挂点，**不要因为它存在就以为现在是异步的**。

### 4.4 为什么码流要绕 `VALLOC_IOCTL_MB_GET_FD`

RV1106 定制 MPP 的 `encode_get_packet()` 返回的是 `struct venc_packet`
（不是通用 `MppPacket` 对象），码流不在用户空间：

```cpp
struct venc_packet encoded_info = {};
MppPacket packet = &encoded_info;            /* 指针就是为了让 mpi 回填 */
mpi->encode_get_packet(ctx, &packet);

struct valloc_mb mb{};
mb.mpi_buf_id = encoded_info.u64priv_data;   /* 拿 MPP 内部 buffer id */
mb.struct_size = sizeof(mb);
ioctl(valloc_fd_, VALLOC_IOCTL_MB_GET_FD, &mb);   /* 换成 dma_buf_fd */
void *p = mmap(nullptr, encoded_info.buf_size, PROT_READ, MAP_SHARED, mb.dma_buf_fd, 0);
fwrite(p + encoded_info.offset, 1, encoded_info.len, raw_file_);
munmap(p, ...); close(mb.dma_buf_fd);
```

`offset` 要判越界（`offset + len > buf_size` 时归零），否则偶发读到脏数据。

### 4.5 为什么先写 `.h265` 再用 ffmpeg 封装

MPP 直接出的是裸 H.265 流（Annex-B），没有 MP4 的 moov/索引。
`remux_mp4()` 用 `-c:v copy` **不重编码**（几乎不耗 CPU），成功后 `unlink` 掉 raw 文件。

```sh
ffmpeg -framerate <fps> -i xxx.mp4.h265 -c:v copy -tag:v hvc1 -movflags +faststart -y xxx.mp4
```

`-tag:v hvc1` 是给 Apple 生态用的，不加某些播放器不认。

## 5. 板端实测基线（可复现，用来对比回归）

| 指标 | 带打点版 | 收打点后（当前） |
|---|---|---|
| 帧数 / 时长 | 63 帧 / 2.10 秒 | 62 帧 / 2.07 秒 |
| 有效帧率 | 30 fps | 30 fps |
| 编码 | `codec_name=hevc`，320×240 | 同 |
| 文件大小 | 71116 字节 | 30996 字节 |
| `alive` 校验 | frame 0→62 全程 1 | 30/60 帧心跳均 1 |
| raw `.h265` | remux 后已 unlink | 同 |

**文件大小会在 30KB～70KB 间浮动**，取决于画面内容（大片暗区/静止画面压缩率高）。
`rc:bps_target = 512kbps` 是 CBR 目标，但 MPP 对极简画面不会硬凑码率，
所以**不要用文件大小判断是否正常**，用帧数和 `ffprobe` 的 `nb_frames`。

**画面校验方法**（判断"生成了文件"≠"画面有效"）：

```sh
ffmpeg -v error -i x.mp4 -vf "scale=8:8,format=gray" -f rawvideo - | \
python3 -c "import sys;d=sys.stdin.buffer.read();n=64
print('帧数',len(d)//n)
for f in [0,3,10,30,len(d)//n-1]:
    p=d[f*n:(f+1)*n]; print(f, '均值%.1f'%(sum(p)/n), min(p), max(p))"
```

正常表现：**前 3～5 帧接近 0（AE 还没收敛），之后均值升到 90～140 并稳定**。
如果全程 0.0 才是真黑屏；如果均值恒定且 min==max，是纯色（多半是没接摄像头或 ISP 没出图）。

## 6. 怎么跑

### 6.1 正常路径（点屏）

主页 →「摄像头」→ 点「录像 H265」→ 再点一次停止。
产物：`/tmp/cam/video_NN_h265.mp4`。

### 6.2 无屏 / 自动化（调试必用）

```sh
S='ssh -i /home/tao/.ssh/id_ed25519 -o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no root@172.32.0.93'

# 直接进摄像头页 + 相机就绪后自动录 2 秒
$S 'export LVGL_LOG=/tmp/h265.log LVGL_START_PAGE=camera CAM_H265_AUTOTEST=1;
    /root/bin/lvgl_daemon.sh restart; sleep 12;
    grep -E "H265|录像" /tmp/h265.log; ls -l /tmp/cam/'
```

三个开关各自的作用（少一个都不行）：

| 开关 | 不给会怎样 |
|---|---|
| `LVGL_START_PAGE=camera` | 停在主页，`CAM_H265_AUTOTEST` 的 tick 不跑，**日志会一片空白** |
| `CAM_H265_AUTOTEST=1` | 不自动起录，必须点屏 |
| `LVGL_LOG=/tmp/xxx.log` | 写进默认 `/tmp/lvgl_super.log`，天气日志每 20 秒刷一条会把证据挤掉 |

> ⚠️ **不要用 `lvgl_daemon.sh log` 抓这些**：它只 `tail -25`。
> 直接 `grep` 日志文件全文。

### 6.3 预期日志（当前静默版）

```text
[APP ] 开始 H265/MP4 录像：/tmp/cam/video_00_h265.mp4  320x240@30fps（上限 10 秒）
[APP ] H265 零拷贝：30 帧完成，src_fd=10 alive=1
[APP ] H265 零拷贝：60 帧完成，src_fd=8 alive=1
[APP ] 录像结束：62 帧 / 2 秒
```

**`alive=1` 是 fd 存活哨兵**（每 30 帧一条，`fcntl(fd, F_GETFD)`）。
看到 `alive=0` 立刻停手，说明有人又把 V4L2 的 fd 关掉了 —— 回去看 §4.1。

要做逐帧排查时，临时把心跳改成每帧（`% 30` → `% 1`）并加 `frame=%d` 打点，
**排完必须收回**，否则每秒 30 行会把 256KB 的日志轮转冲掉。

## 7. 怎么调参数

| 想改什么 | 改哪里 |
|---|---|
| 码率 | `h265_recorder.cpp:175` `const int bps = 512 * 1000;`（CBR 目标，实际随内容浮动） |
| GOP（I 帧间隔） | `h265_recorder.cpp:188` `cfg_s32(cfg, "rc:gop", fps_)` → 当前每 30 帧一个 I |
| 帧率 | `record_start_h265()` 传给 `h265_.start()` 的 `rec_fps_`，同时影响 `rc:fps_*` 与 `rc:gop` |
| QP 范围 | `rc:qp_init/min/max` 那一组（当前 26 / 10 / 51） |
| 录制时长上限 | `cam_capture.hpp:58` `kRecMaxSec = 10`（防写满 27MB tmpfs） |
| 编码格式（H.264） | `mpp_init(..., MPP_VIDEO_CodingHEVC)` → `MPP_VIDEO_CodingAVC`，同时改 `codec:type` 与封装 tag |

**分辨率不用单独改**：`start()` 收的是 `cap_w_/cap_h_`（当前 320×240），
跟着摄像头采集分辨率走。改采集分辨率时注意 NV12 要求 `w*h*3/2` 连续布局，
`submit_dmabuf()` 开头有 `bytes < need` 的校验，不够会直接返回 -1。

## 8. 排查手册

| 症状 | 真正原因 | 第一步 |
|---|---|---|
| 只有 `.h265` 没有 `.mp4`，也没有"录像结束"日志 | `stop()` 没被调用。要么采集停帧导致 `rec_sec_` 不前进，要么根本没停 | `grep 录像结束`；`ls -l /tmp/cam/*.h265` |
| 录了几帧就停、日志无报错 | **V4L2 fd 被 MPP 关掉了**（§4.1），4 帧后 ISP 不再出帧 | 看心跳 `alive=0`；`readlink /proc/$(pidof lvgl_app)/fd/{8,9,10,11}` 是否"已关闭" |
| 屏幕停在最后一帧，像死机 | 可能只是停绘（fbcon 已解绑），也可能 `submit_dmabuf` 持 `rec_mutex_` 卡死 | **先 `pidof lvgl_app`**，进程在就别重启；`cat /proc/<pid>/task/*/wchan` 看是否 `poll_schedule_timeout` |
| 视频开头几帧全黑 | AE 未收敛，**正常** | 用 §5 的亮度脚本确认后面帧有效即可 |
| ffmpeg 报 `Could not find ref with POC n` | 半途起录，开头缺参考帧，只影响前几帧 | `ffprobe -show_entries stream=nb_frames` 完整就不用管 |
| `ffmpeg` 封装失败 | `/tmp` 满（27MB tmpfs）或 raw 文件损坏 | `df -h /tmp`；手动跑一次同条命令看报错 |
| `dlopen librockchip_mpp.so.1 失败` | `/tmp/cam_codec` 没展开（重启后 tmpfs 清空） | `ls /tmp/cam_codec`；跑 `/root/bin/load_h265.sh` |
| 录到 10 秒自动停 | `kRecMaxSec` 上限保护 | 要更长就改常量，同时留意 `/tmp` 余量 |
| 日志一片空白 | 没触发录像（打点只在 `submit_dmabuf` 里） | 检查 `LVGL_START_PAGE=camera` + `CAM_H265_AUTOTEST=1` |

**判断"是不是新二进制在跑"**：部署后必须 `md5sum` 比对宿主与板端。
rootfs 满时 `mv`/scp 会失败但程序照旧跑旧二进制，**日志一切正常**。

## 9. 红线（改代码前必读）

1. **不要把 V4L2 的原 fd 直接交给 MPP**，必须 `dup`（§4.1）。
2. **不要为了"省一次拷贝"把 `mmap` 的指针直接喂给 VENC** —— VENC 要的是 fd/MB，不是用户指针。
3. **不要在 UI 线程里调 `submit_dmabuf` 或 `stop()`**：它持 `rec_mutex_`，会和采集线程互锁。
4. **不要用文件大小判断成没成功**，用 `nb_frames` + 亮度分布。
5. **`/tmp` 是 tmpfs，重启即丢**，重要录像要先拉回宿主；写之前先 `df -h /tmp`。
6. **`malloc`/`new` 的失败路径必须还资源**：本模块曾在高频重试路径漏 200KB/次，
   10MB/s 涨上去把 app 撑死（见 `HANDOVER.md` §5「高频重试函数必须在失败路径还资源」）。
7. 调试打点用完就收，别让常驻版本刷日志。

## 10. 待办 / 可优化

- [ ] 输入 buffer 缓存复用：`start()` 时对所有 V4L2 fd 各 import 一次，`stop()` 统一 put
      （需确认 dup 已生效，见 §4.2）。当前每帧 import/put 实测无性能问题，非必须。
- [ ] `encode_get_packet` 若将来改异步，挪出采集线程，避免持 `rec_mutex_` 长时间阻塞。

- [ ] 输出码流目前 `mmap` + `fwrite` 到文件；可直接写 MP4 分片（fragmented MP4）省掉 remux 一遍 IO。
